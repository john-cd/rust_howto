# Memory Address Pinning

## Give Data a Stable Memory Address with `Pin` {#pinned-data}

[![std][c~std~docs~badge]][c~std~docs]

Moving a value, for example by passing it to a function, can change its address. That matters when a value holds a pointer into itself. After a move, the pointer could still point to the old location. Futures generated by [`async fn`][keyword~async]↗{{hi:async fn}} can hold such references across an `.await`.

[`Pin<Ptr>`][c~std::pin::Pin~docs]↗{{hi:std::pin::Pin}} expresses a guarantee about the **pointee**. Once pinned, an address-sensitive value must remain valid at the same address until it is dropped. The pointer itself can still move. For example, moving a `Pin<Box<T>>` transfers ownership of the box while its contents stay at the same address.

Safe pinning APIs uphold this guarantee. Code that constructs a pin with `unsafe` must uphold it even after the pinned reference goes out of scope. The [`std::pin` module documentation][c~std::pin~docs]↗ describes the full contract.

Most types implement [`Unpin`][c~std::pin::Unpin~docs]↗{{hi:std::pin::Unpin}}, so safe code can move their values even through a pinned mutable reference. Add a [`PhantomPinned`][c~std::marker::PhantomPinned~docs]↗{{hi:std::marker::PhantomPinned}} field to prevent the automatic `Unpin` implementation. A value of that type can still move before it is pinned.
